# ADR-002: REST hacia afuera, gRPC hacia adentro

**Estado:** Aceptada

## Contexto
La arquitectura requiere:
- API pública para Venta-entradas (consumida por frontend, futuros portales, personal)
- Comunicación interna de alto volumen entre Venta-entradas y Aforo (validar stock en cada venta)

## Alternativas consideradas
- **Opción A: Todo REST/JSON** — Simple, universal, cacheable. Pero: JSON verboso, sin tipado estricto, sobrecarga HTTP/1.1, sin streaming nativo.
- **Opción B: Todo gRPC** — Alto rendimiento, tipado fuerte, streaming. Pero: no nativo en browsers (requiere gRPC-Web/Envoy), difícil debugging, no cacheable por proxies estándar, curva de aprendizaje para clientes externos.
- **Opción C: REST público + gRPC interno (elegida)** — Cada protocolo donde encaja mejor.

## Decisión
- **API pública (Venta-entradas → exterior): REST/JSON sobre HTTP/1.1** con OpenAPI, versionado `/v1`, API Key auth.
- **Comunicación interna (Venta-entradas → Aforo): gRPC/Protobuf** con contrato `.proto` versionado, unary RPCs, timeout 3s.

## Justificación
| Factor | REST (público) | gRPC (interno) |
|--------|----------------|----------------|
| Interoperabilidad | Universal (curl, JS, Python, etc.) | Requiere stubs, pero controlamos ambos lados |
| Tipado | OpenAPI (validación runtime) | Protobuf (validación compile-time + runtime) |
| Rendimiento | JSON ~2-3x mayor tamaño | Protobuf binario ~30-60% menor |
| Caché | HTTP caching, ETag, CDN | No cacheable por proxies estándar |
| Debugging | Legible en logs/red | Requiere herramientas (grpcurl, protobuf-decoder) |
| Streaming | SSE/WebSockets aparte | Nativo (unary, server/client/bidi streaming) |
| Ecosistema | Maduro, estándar web | Maduro en microservicios, cloud-native |

**Datos experimentales (Competencia 6)**: En nuestro experimento de timeout, gRPC mostró latencia P99 de 12ms vs 18ms REST para misma operación (ver ADR-004). Protobuf serializó 240 bytes vs 680 bytes JSON (65% reducción).

## Costo aceptado
- **Dual stack**: Mantener dos capas de transporte, serialización, manejo de errores.
- **Tooling**: gRPC requiere `grpcurl`, `protoc` para debugging; no se ve en DevTools del browser.
- **Curva de aprendizaje**: Equipo debe dominar Protobuf, gRPC, interceptors, deadlines.

## Consecuencias
- Contrato `.proto` versionado en repo (T3, T4).
- OpenAPI generado desde FastAPI para REST (T3).
- Experimento midiendo tamaño mensaje y latencia gRPC vs REST.
- Futuro: si se necesita segundo cliente gRPC en otro lenguaje (O5), el contrato `.proto` lo permite.
