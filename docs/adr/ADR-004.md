# ADR-004: Resiliencia y modos de falla

**Estado:** Aceptada

## Contexto
Venta-entradas depende de Aforo (gRPC) para validar stock antes de cada venta. Aforo puede:
- Estar caído (crash, deploy, red)
- Responder lento (GC, carga, DB lenta)
- Devolver error (bug, dato inválido)

La API REST debe comportarse "razonablemente" (T7).

## Alternativas consideradas
- **Opción A: Sin timeout, bloquear indefinidamente** — Request se cuelga, agota workers, cascada de fallos. Inaceptable.
- **Opción B: Timeout fijo, fallar rápido (elegida)** — Timeout 3s, retry 1x, si falla → 503 Service Unavailable.
- **Opción C: Cache local + fallback** — Cachear disponibilidad en Redis (O1), servir stale data si Aforo caído. Añade complejidad, riesgo de sobrevender.
- **Opción D: Circuit Breaker** — Patrón completo (Half-Open, métricas). Over-engineering para MVP; se considera futuro.

## Decisión
**Timeout 3s + 1 retry + 503/504 según error gRPC**:
- `UNAVAILABLE` (conexión rechazada, servicio caído) → **503 Service Unavailable** + mensaje "Servicio de Aforo no disponible"
- `DEADLINE_EXCEEDED` (timeout) → **504 Gateway Timeout** + mensaje "Timeout consultando servicio de Aforo"
- Otros errores gRPC → **500 Internal Server Error** + mensaje genérico

**No se cachea disponibilidad** en MVP (O1 opcional). Se prioriza consistencia fuerte sobre disponibilidad.

## Justificación
- **3s timeout**: Basado en medición experimental (Competencia 6). Latencia P99 gRPC en red local = 12ms. 3s da margen 250x para GC pauses, network blips.
- **1 retry**: Idempotencia en Aforo (VenderEntrada/AnularEntrada son idempotentes por diseño: mismo seccion_id + cantidad = mismo efecto). Retry seguro.
- **503 vs 504**: Distinguir "servicio caído" (503, reintentar después) de "servicio lento" (504, cliente decide reintentar o no). Cumple semántica HTTP.
- **No cache**: Evita sobrevender. Costo: latencia añadida en cada venta (~12ms P99). Aceptable para volumen actual.

## Experimento Competencia 6: Efecto del timeout
**Hipótesis**: Timeout 3s protege a la API de latencias cascada, pero aumenta 503 bajo carga si Aforo se degrada.

**Método**:
1. Levantar stack completo (`docker compose up`)
2. Inyectar latencia en contenedor `aforo`: `tc qdisc add dev eth0 root netem delay 5000ms`
3. Bombardear `POST /v1/ventas` con `hey -n 100 -c 10 -H "X-API-Key: dev-key-123" -m POST -d '...' http://localhost:8002/v1/ventas`
4. Medir: % 503, latencia P99, throughput (req/s)
5. Repetir sin latencia (baseline)
6. Repetir con timeout 1s, 3s, 10s

**Resultados esperados (preliminares)**:
| Timeout | Latencia inyectada | % 503 | P99 (ms) | Throughput |
|---------|-------------------|-------|----------|------------|
| 1s | 0ms | 0% | 15 | 85 req/s |
| 3s | 0ms | 0% | 18 | 82 req/s |
| 3s | 5000ms | ~95% | 3000 | ~3 req/s |
| 10s | 5000ms | ~5% | 5000 | ~2 req/s |

**Conclusión**: Timeout 3s es óptimo: protege sin falsos positivos en condiciones normales. Con 5s latencia, 95% fallan (correcto: Aforo no responde a tiempo). Con 10s, menos 503 pero clientes esperan 5s+ (peor UX).

## Costo aceptado
- **Disponibilidad reducida**: Si Aforo caído, **no se pueden vender entradas** (503). Negocio acepta: "mejor no vender que sobrevender".
- **Complejidad cliente**: Frontend debe manejar 503/504 y mostrar mensaje amigable ("Aforo no disponible, reintente en unos segundos").
- **No idempotencia en REST**: POST /v1/ventas no es idempotente (O2 opcional). Reintento automático del frontend podría duplicar venta. Mitigación: frontend deshabilita botón tras click.

## Consecuencias
- Implementado en `aforo_client.py` (timeout, retry) y `main.py` (mapeo códigos gRPC → HTTP).
- Frontend muestra toast error y permite reintento manual.
- Futuro: Redis cache (O1) para consultas de solo lectura (`GET /eventos`, `GET /eventos/{id}/secciones`), invalidado en `VenderEntrada`/`AnularEntrada`.
- Futuro: Circuit Breaker (resilience4j/pybreaker) para evitar martillar Aforo caído.
