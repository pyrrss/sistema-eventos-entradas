# ADR-003: Contrato, versionado y evolución

**Estado:** Aceptada

## Contexto
Dos contratos independientes:
- **gRPC**: `aforo.proto` (interno, Venta-entradas → Aforo)
- **REST**: `openapi.yaml` (público, exterior → Venta-entradas)

Ambos deben evolucionar sin romper clientes existentes.

## Alternativas consideradas
- **Opción A: Sin versionado** — Cambios in-place. Rompe clientes, no aceptable en producción.
- **Opción B: Versionado en URL (REST) + package en proto (gRPC)** — Explícito, visible en logs, fácil de depurar.
- **Opción C: Versionado por header (Accept) + proto options** — Más RESTful, pero complejo para clientes y debugging.

## Decisión
- **REST**: Prefijo `/v1/` en todas las rutas (`/v1/asistentes`, `/v1/ventas`, `/v1/eventos/...`). OpenAPI servido en `/v1/openapi.json`.
- **gRPC**: Package `aforo.v1` en `.proto`. Cambios compatibles solo (añadir campos opcionales, nuevos métodos). Cambios breaking → nuevo package `aforo.v2` y nuevo servicio.

## Reglas de compatibilidad

### gRPC (Protobuf)
| Cambio | Compatible? | Acción |
|--------|-------------|--------|
| Añadir campo opcional (nuevo número de tag) | ✅ | Sí, usar `optional` |
| Añadir nuevo método al servicio | ✅ | Sí, clientes viejos no lo llaman |
| Cambiar tipo de campo | ❌ | Nuevo tag + campo, deprecar viejo |
| Eliminar campo | ⚠️ | Marcar `reserved`, no reutilizar tag |
| Cambiar nombre de campo | ✅ | Solo metadata, wire format usa tag |
| Cambiar de unary a streaming | ❌ | Nuevo método con nombre distinto |

### REST (OpenAPI)
| Cambio | Compatible? | Acción |
|--------|-------------|--------|
| Añadir campo opcional en response | ✅ | Clientes ignoran campos extra |
| Añadir query param opcional | ✅ | Clientes no lo envían |
| Añadir nuevo endpoint | ✅ | No afecta existentes |
| Cambiar tipo de campo | ❌ | Nueva versión `/v2/...` |
| Eliminar campo en response | ⚠️ | Solo si deprecated y v2 |
| Cambiar código de estado | ❌ | Nueva versión |

## Notificación a consumidores
- **Internos (gRPC)**: Mismo repo, deploy atómico. Consumidor (Venta-entradas) actualiza stubs al compilar.
- **Externos (REST)**: Changelog en repo, headers `Deprecation` y `Sunset` en respuestas, 3 meses aviso antes de retirar `/v1`.

## Costo aceptado
- **Duplicación de esfuerzo**: Mantener dos esquemas de versionado.
- **Migración gradual**: Período donde conviven v1 y v2.
- **Testing de contrato**: Requiere tests que validen compatibilidad (O4).

## Consecuencias
- Archivos versionados en repo: `aforo.proto` (package `aforo.v1`), `openapi.yaml` (servers `/v1`).
- ADR-004 define manejo de fallas durante migración.
- Experimento Competencia 6: medir impacto de cambios de contrato en latencia.
