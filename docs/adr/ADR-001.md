# ADR-001: Estilo de integración y descomposición en servicios

**Estado:** Aceptada

## Contexto
La Productora de Eventos EscenaViva tiene dos sistemas heredados que nunca se integraron:
- **Aforo**: Fuente de verdad sobre eventos, secciones y disponibilidad. Administra la capacidad.
- **Venta de Entradas**: Registra asistentes y ventas. Necesita consultar disponibilidad antes de vender.

Hoy se venden más entradas que asientos porque cada punto de venta lleva su propia cuenta. Se requiere una integración que garantice consistencia.

## Alternativas consideradas
- **Opción A: Monolito único** — Un solo servicio con ambas bases de datos. Simple de desarrollar, pero acopla dominios distintos, dificulta escalar independientemente y rompe el principio de base de datos por servicio.
- **Opción B: Dos servicios con base de datos compartida** — Ambos acceden a la misma BD. Rompe aislamiento, crea acoplamiento por esquema, y no permite evolución independiente.
- **Opción C: Dos servicios con base de datos por servicio (elegida)** — Cada servicio tiene su propia BD. Aforo expone gRPC interno; Venta-entradas expone REST público. Comunicación sincrónica para validar stock.

## Decisión
Descomponer en **dos microservicios** con **base de datos por servicio**, comunicación **REST hacia afuera, gRPC hacia adentro**.

## Justificación
- **Bounded contexts** claros: Aforo = catálogo/disponibilidad; Ventas = transacciones/asistentes.
- **Autonomía**: Cada equipo puede evolucionar su servicio y BD sin coordinar despliegues.
- **Consistencia**: Venta-entradas consulta a Aforo *antes* de persistir, garantizando que no se sobrevenda.
- **Rendimiento**: gRPC binario + HTTP/2 para comunicación interna de alto volumen.

## Costo aceptado
- **Duplicación intencional**: Venta-entradas guarda `nombre_evento`, `nombre_seccion`, `id_seccion_aforo` (referencia cruzada) para no necesitar joins distribuidos al listar ventas.
- **Complejidad operacional**: Dos BD, dos despliegues, red entre servicios.
- **Latencia añadida**: Cada venta requiere un round-trip gRPC a Aforo (~2-5ms en red local).

## Consecuencias
- Requiere manejo de fallas (T7): timeouts, circuit breaker, respuesta 503 si Aforo caído.
- Contratos versionados: `.proto` para gRPC, OpenAPI para REST.
- Experimento Competencia 6: medir latencia con/sin timeout, efecto de caché futuro.
